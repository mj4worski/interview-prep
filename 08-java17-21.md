# Java 17 i 21 — tylko to, co wychodzi na rozmowie

Masz 11 lat. Nie recytuj JEP-ów. Pokaż, kiedy byś tego użył w Springu.

Mechanizm jest pod przykładami. Oficjalne strony, które wystarczą, są w `09-materialy.md`: dokument języka plus motywacja JEP-a, nie wątek na liście dyskusyjnej.

## Java 17 (LTS) — must

### Record

Niemutowalny nośnik danych. `equals`/`hashCode`/`toString` za darmo.

```java
public record Money(long cents, String currency) {
    public Money {
        if (cents < 0) throw new IllegalArgumentException("cents");
        currency = currency.toUpperCase();
    }
}
```

Kiedy: DTO, event Kafka, wartość w domenie. Nie: encja JPA (Hibernate chce no-arg + mutowalne pola; da się, ból).

### Co dostajesz od kompilatora

Record to klasa z polami `final`, kanonicznym konstruktorem, `equals` / `hashCode` / `toString` ze składowych i akcesorami o nazwie pola (`cents()`, nie `getCents()`).

Kompaktowy konstruktor `public Money { ... }` jest ciałem kanonicznego konstruktora. Przypisanie `currency = currency.toUpperCase()` zmienia parametr, zanim pole zostanie ustawione. Walidacja tu jest jedynym miejscem, w którym da się obronić niezmiennik. Setteru nie ma.

`equals` porównuje składowe. Dwa `Money(100, "PLN")` są równe i mają ten sam hash, więc record nadaje się na klucz mapy, dopóki składowe same są niemutowalne. `List` w składowej recordu psuje to, bo lista da się zmienić po włożeniu do mapy.

Dziedziczenie po recordzie nie istnieje. Wspólny typ robisz interfejsem, często sealed. Jackson i rekordy w Springu działają (kanoniczny konstruktor jest tym, czego potrzebuje deserializacja). Hibernate na encji nadal chce pusty konstruktor i pola do zapisu dirty checkingu. Record jako projekcja zapytania (`interface` albo DTO z `@Query`) jest OK, record jako `@Entity` na tej rozmowie odpuszczasz.

[Records](https://docs.oracle.com/en/java/javase/21/language/records.html), motywacja: [JEP 395](https://openjdk.org/jeps/395).

### Sealed + pattern matching switch

Zamknięta hierarchia zamiast otwartego `interface` + 15 implementacji.

```java
sealed interface PaymentResult permits Paid, Failed, Pending {}
record Paid(String txId) implements PaymentResult {}
record Failed(String reason) implements PaymentResult {}
record Pending(String txId) implements PaymentResult {}

static String msg(PaymentResult r) {
    return switch (r) {
        case Paid(var id) -> "ok " + id;
        case Failed(var reason) -> "fail " + reason;
        case Pending(var id) -> "wait " + id;
    };
}
```

Kompilator wymusza kompletność. To argument za sealed: nowy wariant nie przejdzie cicho.

### Co się stanie, jak dojdzie czwarty stan

`PaymentResult` bez sealed da się zaimplementować w innym module. `switch` z `default` połknie nowy typ i zwróci coś ogólnego. Dowiesz się na produkcji.

`sealed` + `permits` zamyka listę. Nowy `record Refund(...)` bez dopisania do `permits` się nie skompiluje. Po dopisaniu switch bez gałęzi `Refund` też się nie skompiluje, o ile nie ma `default`. `default` celowo rozszczelnia tę gwarancję. Na rozmowie mówisz, że `default` wklejasz tylko, gdy świadomie chcesz „reszta tak samo”.

Pattern `case Paid(var id)` wyciąga składową bez rzutowania i bez `instanceof` plus getter. To jest ten sam mechanizm co record: kształt jest znany kompilatorowi.

[Sealed](https://docs.oracle.com/en/java/javase/21/language/sealed-classes-and-interfaces.html), [JEP 409](https://openjdk.org/jeps/409), switch: [JEP 441](https://openjdk.org/jeps/441).

### Text blocks

JSON/SQL w testach i skryptach. `"""..."""`. Nie do budowania SQL z user input (nadal injection).

### Switch expressions

`switch` jako wyrażenie, `yield` w bloku, no fall-through przy `->`.

### `var` + diamond

Lokalnie OK gdy typ widać z prawej. Nie w API publicznym. Nie `var x = null`.

### HttpClient (11+, ale pytają przy 17)

Wbudowany, async. W Springu i tak WebClient/RestClient. Wiedz, że jest.

## Java 21 (LTS) — must

### Virtual threads

Lekki wątek na carrierze. Model: **request = wątek** znowu ma sens przy IO.

Tak: dużo równoległego IO (HTTP out, JDBC, Kafka sync consumer), Tomcat z virtual na 21.

Nie: ciężki CPU (nie przyspieszysz), pinowanie (`synchronized` długo na native, JNI). Pinned carrier = uciekła równoległość.

Pula: `Executors.newVirtualThreadPerTaskExecutor()`. Nie kopiuj `core=200` z platform threads.

Ze Spring Boot 3.2+: `spring.threads.virtual.enabled=true`. Na rozmowie: „IO-bound serwis tak; najpierw zmierz, pinning i ThreadLocal w bibliotekach mogą boleć.”

ThreadLocal: działa, ale przy milionie VT jest drożej. W 21+ jest też scoped value (wspomnij, nie implementuj).

### Carrier, montowanie, pinning

Wątek platformowy to wątek systemu, ze stosem rzędu megabajta. Tysiąc równoległych requestów to tysiąc takich stosów i tysiąc slotów w puli, nawet gdy 990 z nich śpi na sockecie.

Wątek wirtualny jest obiektem w Javie. Pula carrierów (wątki platformowe, z grubsza tyle co rdzenie) wykonuje je. Gdy wirtualny dochodzi do blokującego I/O zrobionego po stronie JDK (odczyt socketu, parking), JVM zdejmuje go z carriera i carrier bierze innego wirtualnego, który ma co liczyć. Po przyjściu danych wirtualny jest wznawiany, niekoniecznie na tym samym carrierze.

Stąd „request = wątek” znowu ma sens: piszesz zwykły, blokujący kod, a sen na I/O nie zajmuje carriera. Nie dostajesz szybszego CPU. Pętla licząca hash zajmuje carriera tak samo jak wątek platformowy.

Pinning na 21: wirtualny wewnątrz `synchronized` albo w ramce natywnej nie schodzi z carriera na czas blokady. Carrier stoi razem z nim. Dużo takich miejsc pod obciążeniem kończy się kolejką, której pula 200 wątków platformowych nie miała, bo tam limit był jawny. Od JDK 24 pinowanie na `synchronized` jest zdjęte (JEP 491). Rozmowa o 21 nadal pyta o pinning. Mówisz, przy której wersji jesteś.

`ThreadLocal` na wirtualnym działa i jest kopiowany razem z nim. Milion wirtualnych z ciężkim ThreadLocalem to milion kopii. Scoped values są odpowiedzią „wartość na czas wywołania, bez kopiowania w dół”, w 21 jako preview. Wspominasz problem, nie piszesz API z głowy.

Spring Boot: `spring.threads.virtual.enabled=true` przełącza Tomcata i executory na wirtualne. Wirtualne są daemonami. Aplikacja, którą przy życiu trzymał tylko `@Scheduled`, może wyjść, gdy zostanie sam scheduler. Do tego jest `spring.main.keep-alive=true`. Pula JDBC się nie powiększa sama: 2000 wirtualnych requestów na puli 20 połączeń stoi w kolejce do bazy. Najpierw mierzysz pulę, nie „włączam, bo 21”.

[Virtual threads](https://docs.oracle.com/en/java/javase/21/core/virtual-threads.html), [JEP 444](https://openjdk.org/jeps/444), [Spring Boot](https://docs.spring.io/spring-boot/reference/features/spring-application.html#features.spring-application.virtual-threads).

### Sequenced collections

`getFirst()` / `getLast()` / `reversed()` na `List`, `LinkedHashMap`. Drobiazg, czasem jako ciekawostka.

### Record patterns / pattern matching dojrzalsze

Rozpakowujesz record w `instanceof` i `switch`. Ten sam motyw co wyżej.

### Structured concurrency (preview w 21)

„Uruchom 3 IO, anuluj resztę jak jedno padnie.” Preview — powiedz że znasz problem (leak tasków w `invokeAll`), nie koduj API z głowy.

## Co zostaje z Javy 8–11, bo i tak pytają

- `Optional` tylko return, `orElseGet`
- Stream: czytelność > spryt; `parallelStream` nie default
- `CompletableFuture` vs virtual thread: VT prostszy do sekwencyjnego IO; CF gdy składasz wiele async bez blokowania
- `HttpClient`, `var`, factory `List.of` (immutable, nie akceptuje null)

## Grill

**Record vs Lombok `@Value`?**
Record to język, kanoniczny konstruktor, deconstruction. Lombok to generowanie. W nowym kodzie 17+ record na DTO.

**Czemu sealed?**
Jawny zbiór wariantów + wyczerpujący switch. Lepsze niż runtime `if-else` i otwarty inheritance.

**Virtual threads zamiast WebFlux?**
Często tak dla zespołu imperatywnego. WebFlux zostaje gdy już macie reactive stack / streaming backpressure. Nie przepisuj wszystkiego w tydzień.

**Czy record jako klucz w HashMap?**
Tak, jeśli składowe niemutowalne i dobrze zdefiniowane. To jedna z zalet.
